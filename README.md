# mini_fkdb —— 带外键约束的自写关系存储引擎

不依赖任何现成数据库或第三方库（纯 Python 3.9 标准库），从二进制存储、
WAL 恢复、锁管理到外键级联语义全部自己实现。起因是一次真实事故：
客服后台删除一个大客户，数据库沿订单→明细→物流→发票→领券记录层层
级联删了几百万行、锁表二十分钟，还因为几张表配了“删除置空”留下一堆
没有归属的发票。本项目把这件事做成可预估、可拆批、可核对、全程无悬空
外键的存储引擎，并配了一个 20 张表的电商库和 Web 控制台复现/验证。

## 它满足的五条要求

1. **外键动作齐全**：`CASCADE / SET NULL / SET DEFAULT / RESTRICT /
   NO ACTION`，删除和被引用键更新（ON UPDATE）都支持，多层多分支按
   SQL 标准的最小不动点语义传播。
2. **复杂图结构**：自引用树（分类/客户/菜单）、一张表多条外键指向同一张
   表（订单的下单人与审批人、物流的发货/收货地址）、三张表成环
   （products→brands→categories→products，以及工单↔订单）。同一次删除
   无论从哪条路径先走到某个行，结果逐行相同（有专门的路径无关测试）。
3. **删除前预估**：返回每张表删多少行、置空/置默认多少列、会不会被
   RESTRICT/NO ACTION 挡住、最大级联深度。预估与执行共用同一份规划代码，
   逐表核对。
4. **拆批执行**：大删除拆成多个短事务，每批持锁行和时间有限，业务事务
   可在批间穿插；最终行集合与一次删完完全相同；严格两阶段锁保证任何
   提交点都读不到指向不存在行的外键。
5. **可追溯清单**：每个被删/置空的行都记录它是经由哪条外键链传播过来的，
   含多分支的备选路径；Web 页面可选任意一行看级联影响树。

## 架构

```
mini_fkdb/
  schema.py      表/列/外键/目录，JSON 落盘
  codec.py       手写二进制：堆帧、WAL 帧、zigzag varint 行编解码
  locking.py     行级 S/X 锁，FIFO 公平授予，等待图死锁检测，等待计时
  storage.py     堆文件(append-only) + WAL + 内存主键/外键索引 + 崩溃恢复
  planner.py     级联规划器（不动点遍历，预估/执行同源，路径无关）
  transaction.py 严格 2PL 事务、DML、计划执行、可延迟外键（环插入）
  db.py          引擎门面、一次性/拆批级联删除、预估核对
ecommerce/       20 张表电商模型 + 确定性数据生成器
experiments/     并发业务负载 + 全套验收实验
webui/           标准库 http.server + 原生 JS 控制台
tests/           烟囱测试 + 27 项语义测试
```

### 存储与恢复

- 每张表一个堆文件，行帧 `magic|flags|rowid|lsn|len|payload`，更新/删除
  追加新版本帧，内存偏移表只认最新版。
- 写事务：所有改动先追加 WAL 数据帧并 fsync，再写提交帧（原子提交点），
  然后在存储全局锁内一次性应用到堆文件和内存索引——读者要么看到全部
  改动、要么看不到。
- 崩溃恢复：堆文件尾部残缺帧截断；扫堆重建主键和外键索引；重放 WAL 中
  已提交且 lsn 更新的帧，未提交事务天然被忽略。

### 为什么不会有悬空外键

- 插入/更新子行时对父行加 S 锁并校验存在性；删除父行要 X 锁。两类操作在
  同一把行锁上互斥，“删父行的同时插入悬空子行”在锁层面不可能发生。
- 级联删除在一个事务内完成全部关联改动，锁持有到提交，别的事务不可能
  读到“父行已删、子行还挂着”的中间态。
- 拆批模式下每个分片都是完整事务，提交即一致；实验里有并发读线程持续
  校验引用完整性，观测到的悬空引用数必须为 0。

### RESTRICT 与 NO ACTION 的区别

- `RESTRICT`：语句开始即检查，立即阻止。
- `NO ACTION`：延迟到语句末检查；如果冲突子行在这期间被另一条 CASCADE
  边级联删掉或被 SET NULL/DEFAULT 处理掉（环里的自消解），就不再违反。
  测试 `test_restrict_vs_no_action` 专门覆盖这个标准差异。

## 使用

所有命令都用 `-I`（隔离模式）跑，通过 `run.py` 注入项目路径：

```bash
# 跑全部测试
python3 -I run.py test

# 生成电商库（--ka-orders 让大客户承载百万级关联行）
python3 -I run.py gen --db data/shop --customers 2000 --ka-orders 150000

# 全套验收实验：逐客户预估核对 / RESTRICT 拦截 / 一次删 vs 拆批并发对比
python3 -I run.py exp --db data/shop --out experiments/out \
    --workers 4 --batch-size 25

# Web 控制台：选行看影响树、批量预估、执行删除、看实验报告
python3 -I run.py web --db data/shop --port 8000
```

### 编程接口速览

```python
from mini_fkdb import Database, Catalog, Column, ForeignKey, CASCADE, SET_NULL
db = Database.create(path, catalog)

# 预估（只读，不动数据）
plan = db.estimate_delete([("customers", 1)])
plan.counts_by_table()          # 每张表的动作计数
plan.impact_tree()              # 级联影响树

# 一次性级联删除（内部自动核对预估与实际）
report = db.cascade_delete([("customers", 1)])

# 拆批删除（短事务分片，业务可穿插）
manifest = db.cascade_delete_batched([("customers", 1)], batch_size=25)

db.dangling_refs()              # 全库悬空外键自检，正常为 []
```

## 拆批为什么不会悬空、也不会被环卡住

大删除按“叶子锚点先行、根最后删”拆成多个短事务。但像电商里
`s.support_tickets.order_id` 这种 `NO ACTION` 边会带来一个问题：先删订单时，
工单还活着，按标准语义本该阻止。可在一次性删除里，工单本会经
`customer_id` 的 CASCADE 路径随大客户一起删掉，约束其实会自消解。

引擎用 `Database.execute_expanding_batch` 处理：

1. 先对全部根做一次全量预估，得到**全局删除闭包**（哪些行最终必被删）。
2. 每个分片单独预估执行；若被 NO ACTION/RESTRICT 挡住，检查阻挡行是否
   在全局闭包里：
   - 在 → 把它吸收进当前分片、**同一事务**删掉，约束自消解；
   - 不在 → 它本不该被删，按标准语义报错，整个分片零改动。
3. 每个分片都是完整事务，提交即一致，提交点悬空外键恒为 0。

这样既保留了短事务持锁短、业务可穿插的好处，又和一次性删除的最终行集合
逐表相同（有等价性测试和每次提交点的零悬空检查兜底）。

## 规模实测（笔记本 Darwin / Python 3.9，纯标准库）

数据生成（bulk loader 直写堆文件）：

| 项目 | 数值 |
|---|---|
| 数据量 | 174 万行 / 20 张表 / 堆文件约 120MB |
| 生成耗时 | 约 18 秒 |
| 大客户关联删除规模 | 约 169 万行，删除后悬空外键 0 |

并发删除对比（4 个业务线程，其中 25% 操作直接读大客户热行；
完整数字见 `experiments/out/million_bench.json`）：

| 指标 | 一次性大事务 | 拆批（301 个短事务） |
|---|---|---|
| 删除墙钟时间 | 154.6 s | 77.4 s |
| 业务操作吞吐 | 9399 个 | 20875 个（约 2.2 倍） |
| 热行读**最大等待** | 27788 ms | 372 ms（降约 75 倍） |
| 业务累计锁等待 | 74581 ms | 1396 ms（降约 53 倍） |
| 最终行集合 | — | 与一次性逐表相同 |
| 悬空外键 | 0 | 每个分片提交点都是 0 |

> 关键不是“拆批一定更快”，而是它把单个巨型事务的长持锁切成有界短持锁：
> 墙钟时间可能相近甚至略长，但任何单个业务操作都不会被卡几十秒。
> 普通业务操作不碰大客户的行时，靠行级锁本来就几乎不被阻塞——
> 这正是相对“整表锁住”的根本改进。

常规功能验收（小库、含逐客户预估核对、RESTRICT 拦截、外键链清单）见
`experiments/out/report.json`；复跑百万行基准用
`python3 -I experiments/million_bench.py --db <百万行库> --out experiments/out`。
